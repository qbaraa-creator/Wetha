# طقس جدة — الرياح والرطوبة

تطبيق ويب تقدمي (PWA) عربي RTL ينفّذ وثيقة `PRD_Jeddah_Wind_Humidity_Weather_App_v1.0_AR.md` الإصدار 1.0.

يعرض توقع سبعة أيام لجدة في صفحة واحدة، مع ملخص أعلى الصفحة للساعات المناسبة خلال الأيام الخمسة
القادمة. يجتمع محورَا **الرياح** و**الرطوبة** في شريط زمني واحد بطبقتين مستقلتين، بلا «تقييم طقس عام»
يخلطهما.

---

## التشغيل المحلي

```bash
npm install
```

```bash
npm run dev
```

يفتح على `http://localhost:5173` افتراضيًا.

## الاختبارات

```bash
npm test
```

154 اختبارًا آليًا تغطي قواعد المجال وعقد المزود ومدقق التخزين ومكوّنات الواجهة،
بما فيها لوحة المفاتيح واللمس وRTL ورسائل الخطأ والتحذير والبيانات القديمة.

اختبار التكامل يتصل بالمزود فعليًا ويتحقق من عقده — خاصة وحدة `moon_phase` — ولا يعمل افتراضيًا
حتى لا يعتمد البناء على الشبكة:

```bash
npm run test:integration
```

بعد البناء يمكن فحص سلامة مخرجات PWA، ومسارات الملفات، وسياسة المحتوى، وملف Service Worker:

```bash
npm run test:pwa
```

## البناء والنشر

```bash
npm run build
```

يُنتج مجلد `dist` جاهزًا للرفع على أي استضافة ملفات ساكنة (Netlify، Vercel، GitHub Pages، Cloudflare Pages).
لا يوجد Backend ولا مفاتيح API. المسار الأساسي نسبي افتراضيًا، ويمكن ضبطه وقت البناء عبر `VITE_BASE_PATH`:

```bash
VITE_BASE_PATH=/اسم-المستودع/ npm run build
```

معاينة النسخة المبنية محليًا:

```bash
npm run preview
```

إعادة توليد أيقونات PWA بعد أي تغيير في هوية الأيقونة:

```bash
npm run icons
```

### النشر على GitHub Pages

يتضمن المشروع سير عمل في [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml). عند الدفع إلى فرع
`main` يشغّل الاختبارات والبناء وفحص PWA، ثم ينشر `dist`. يحسب السير تلقائيًا المسار الصحيح سواء كان
المستودع موقع الحساب (`owner.github.io`) أو موقع مشروع (`owner.github.io/repository`).

بعد إنشاء المستودع ورفعه، اختر في GitHub: **Settings → Pages → Source: GitHub Actions**. لا يحتاج
المشروع إلى أسرار أو مفاتيح API. يتابع Dependabot تحديث حزم npm وإجراءات GitHub دوريًا.

## أين تُعدَّل الإعدادات

كل ما هو قابل للضبط في ملف واحد: [`src/config/appConfig.ts`](src/config/appConfig.ts).

| ما تريد تغييره | الثابت |
|---|---|
| الموقع والإحداثيات والمنطقة الزمنية | `LOCATION` |
| عدد أيام التوقع | `FORECAST_DAYS` |
| عتبات سرعة الرياح | `SPEED_THRESHOLDS` |
| عتبات الرطوبة | `HUMIDITY_THRESHOLDS` |
| لون كل قطاع اتجاه | `DIRECTION_SEVERITY` |
| نسبة الاتجاه العام قبل وصف الرياح بالمتقلبة | `DOMINANT_DIRECTION_MIN_SHARE` |
| مهل التحديث والمهلة الزمنية وإعادة المحاولة | `REFRESH_POLICY` |
| ألوان الحالات وأسماؤها ورموزها | `SEVERITY_COLORS` و`SEVERITY_LABELS` و`SEVERITY_GLYPHS` |
| نسبة مصدر البيانات | `DATA_ATTRIBUTION` |

تغيير المدينة لا يتطلب لمس أي مكوّن أو أي قاعدة تصنيف: عدّل `LOCATION` فقط.
قيم الألوان مكرّرة كمتغيرات CSS في أعلى [`src/styles.css`](src/styles.css) لأن المتصفح يحتاجها للرسم؛
هي المكان الوحيد الآخر الذي يذكر قيمة لون.

## قرارات تنفيذ مثبتة

- **تنعيم الاتجاه يغيّر الاتجاه واللون معًا.** الساعة الشاذة الوحيدة المحاطة باتجاه واحد تُدمج معه
  ويُعاد حساب حالتها من الاتجاه الجديد؛ ولذلك وُضع استثناء القسم 5.6: الساعة التي حالتها الخام حمراء
  لا تُدمج أبدًا. يظهر في التفاصيل الساعية نجمة `*` على كل ساعة مُنعَّمة حتى يبقى الأمر قابلًا للتحقق.
- **ساعات اليوم الحالي المنقضية تدخل** في المتوسطات وعدّادات الألوان وترتيب الأسبوع، لأن القسم 1.3
  يعرّف اليوم بأنه `00:00–24:00`. تُخفَّف بصريًا فقط كما في القسم 10.2.
- **لا توجد صفحة يوم مكررة**: كل يوم يفتح تفاصيله داخل بطاقة الأسبوع الأصلية، فبقي مسار قراءة واحد.
- **الشريط الساعي مركّب بطبقتين**: النصف الأعلى للرياح والأسفل للرطوبة، مع محور وهدف لمس واحد.
  وهو محطة Tab واحدة مع تنقّل بالأسهم داخلها (`role="listbox"`)، بدل 24 محطة لكل شريط.
  التفاصيل تُعلن في لوحة `aria-live` أسفل الشريط، فلا يعتمد التلميح على Hover وحده (القسمان 9.3 و21.7).
- **الأنماط تسند الألوان في الأشرطة**: أخضر سادة، برتقالي مخطط صاعد، أحمر مخطط هابط وأغمق،
  فتبقى الحالات مميزة في التدرج الرمادي.
- **أسماء الألوان لا تتكرر بصريًا** بجانب كل رمز؛ تبقى في `aria-label` و`title` لقارئات الشاشة
  ولمن يحتاج تفسير الحالة.
- **الوحدة غير المتوقعة تُرفض ولا تُحوَّل صامتًا**: يُفرَّغ الحقل ويُسجَّل تنبيه تقني في `forecast.warnings`.
- **البيانات الخارجية لا تُوثق ضمنيًا**: تُفحص استجابة المزود والمصفوفات والوحدات والنطاقات والمنطقة الزمنية،
  كما يُرفض سجل التخزين كاملًا إذا خالف المخطط الداخلي.

## الحماية

- سياسة محتوى (CSP) تقصر السكربتات والموارد على الموقع، والاتصال الشبكي على Open-Meteo فقط.
- لا تُحقن استجابة المزود كـ HTML، ولا توجد رموز وصول أو أسرار في المتصفح.
- سياسة Referrer مقيدة، ومصادر النماذج والكائنات محظورة.
- فحص `npm audit` جزء من مراجعة الإطلاق، وتوجد تحديثات Dependabot مجدولة.
- توجد [سياسة إبلاغ أمني](SECURITY.md) مهيأة لاستخدام تقارير GitHub الخاصة بدل كشف الثغرات علنًا.

> GitHub Pages يفرض HTTPS، لكنه لا يتيح ضبط رؤوس HTTP مخصصة لكل مشروع. لذلك سياسة المحتوى موضوعة
> في HTML. إذا نُقل التطبيق إلى استضافة تدعم الرؤوس، يُفضّل إرسال CSP و`X-Content-Type-Options`
> و`Permissions-Policy` كرؤوس HTTP أيضًا.

## مصدر البيانات

[Open-Meteo Forecast API](https://open-meteo.com/) — بلا مفتاح، مع دعم CORS، بوضع `Best Match`.

النسبة معروضة في تذييل التطبيق كما يوجب الترخيص (FR-16).
**قبل أي استخدام تجاري** يجب مراجعة خطة الاستخدام التجاري وشروطها؛ شروط الاستخدام الشخصي لا تمتد
تلقائيًا إلى الاستخدام التجاري.

القيم توقعات نموذجية وليست قياسات محطة محلية لحظية، والواجهة تصرّح بذلك.

## ما لم يُنفَّذ في هذه الجولة

هذه هي قائمة الانحرافات عن الوثيقة (مطلوبة بموجب القسم 26):

1. **صور أو تسجيل قصير للواجهة** (القسم 26، البند 8): جرت مراجعة بصرية فعلية عند 320 و768 و1440 بكسل
   وأُصلحت مشكلات ظهرت فيها، لكن لم تُصدَّر ملفات صور إلى المستودع.
2. **اختبار Safari على iOS وmacOS وEdge** (القسم 20 — التوافق): البناء يستخدم خصائص CSS منطقية
   (`inset-inline-start`) و`IndexedDB` وService Worker، وكلها مدعومة في آخر إصدارين من هذه المتصفحات،
   لكن لم يجرِ فتح فعلي عليها.
3. **رابط نسخة اختبار منشورة** (القسم 26، البند 2): إعداد GitHub Actions جاهز، لكن إنشاء المستودع
   والدفع إليه وتفعيل Pages لم يُنفّذ بعد لأنه يحتاج حساب GitHub والوجهة التي يختارها مالك المشروع.

ما عدا ذلك، جميع متطلبات `Must` في القسم 11 وجميع اختبارات الحدود في القسم 21 منفَّذة وناجحة.
